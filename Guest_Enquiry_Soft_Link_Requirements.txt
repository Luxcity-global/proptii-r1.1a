Guest Enquiry & Soft-Link System
Product Requirements & Flow Document
Proptii Communication / Messaging

1. Overview
This document defines the requirements and end-to-end flow for capturing guest (unauthenticated) user
details on the property listing platform.
•
•
•
•

Collect the guest’s contact details via a Quick Request modal.
Create a temporary “soft” account (ghost account) for both the enquiring tenant and the receiving
landlord if neither is registered.
Enable threaded email-based messaging between both parties without requiring sign-up.
Trigger account-claim emails to both parties once a reply is exchanged, inviting them to register
and retain their conversation history.

2. Actors & Definitions
Actor

Definition

Guest Tenant

An unauthenticated user browsing properties. Has not registered an account.

Ghost Tenant

A system-generated soft account created when a guest tenant submits an enquiry.
Identified by email only.

Platform Landlord

A registered landlord who owns listings on the platform.

External Landlord

A landlord whose listing was scraped from OnTheMove or RightMarket. Not registered
on the platform.

Ghost Landlord

A system-generated soft account representing an external landlord. Created when a
tenant enquires about a scraped listing.

Claimed Account

A ghost account (tenant or landlord) that has been converted into a full registered
account after following the claim email link.

4. Ghost Account (Soft Link) Creation
4.1 Ghost Tenant Account
When a guest submits the Quick Request form, the system checks whether an account exists for the
provided email address.
Condition

Action

Email does not exist

Create ghost_tenant record. Set status = ‘ghost’, source = ‘quick_request’,
created_at = now.

Email exists (full account)

Attach enquiry to existing account. Prompt user to log in for full
conversation access.

Email exists (ghost)

Reuse ghost account. Append new enquiry thread. Do not create a
duplicate.

4.2 Ghost Landlord Account (Scraped Listings)
For listings sourced from OnTheMove or RightMarket, the original landlord is not on the platform. A ghost
landlord account is created to hold the enquiry thread.
•
•
•
•

Ghost landlord is identified by the scraped contact email or phone (if available from the listing
source).
If no contact detail is available, the enquiry is queued and the system marks the listing as
“enquiry pending”.
Ghost landlord record stores: source_platform (e.g. “onthemove”), external_listing_id,
scraped_contact_email (nullable), status = ‘ghost’.
The platform may forward the message to the scraped contact email on behalf of the guest.

5. Messaging Thread — Guest Conversation Flow
5.1 Thread Creation
1. Guest submits Quick Request. Ghost tenant account is created (or matched).
2. System creates an enquiry_thread record linked to: ghost_tenant_id, listing_id, landlord_id
(platform or ghost).
3. A unique thread_token is generated for tokenised email replies.
4. The enquiry message is stored as the first message in the thread.

5.2 Email Relay Mechanism
All messages between ghost users are relayed via the platform’s email relay system. This enables a
conversation without either party needing to log in.
•
•
•
•
•

Each thread has a unique relay address: reply+{thread_token}@mail.yourplatform.com
When a landlord replies (by email), the platform parses the inbound email, extracts the reply
body, strips quoted history, and appends it to the thread.
The tenant receives a notification email with the reply embedded and a “Reply” button linking
back to a tokenised reply page.
The tenant can reply via the tokenised web page or directly by replying to the notification email.
A maximum thread depth of 20 messages is enforced for ghost threads. Beyond this, users must
claim accounts.

7. Account Claim Flow
7.1 Claim Page (/claim?token=...)
8. User lands on claim page via email link.
9. System validates token: exists, not expired, status = ‘claim_email_sent’.
10. Pre-fill registration form with known data (email, name if available).
11. User sets password (or continues via Google/Facebook/Twitter).
12. On successful registration:
• ghost_account.status = ‘claimed’, claimed_at = now.
• ghost_account.claim_token = null (invalidated).
• Link full user account to all historical threads.
• All past messages and enquiries are migrated to the new account.
13. User is redirected to their inbox/conversation dashboard.

7.2 Token Expiry Handling
•
•
•

If claim_token is expired: show message “This link has expired” + button to request a new one.
Re-send endpoint: POST /claim/resend — accepts email, issues new token if ghost account
exists.
Ghost accounts with status = ‘ghost’ (no reply received) do not receive claim emails proactively.

7.3 Merged Account Rules
•
•
•

If a user registers with an email that matches a ghost account, auto-merge on email verification.
All ghost threads are reassigned to the full account.
Ghost account record is soft-deleted (retained for audit; not surfaced in UI).

9. Scraped Listing Handling — OnTheMove & RightMarket
9.1 Listing Metadata
•
•
•

Each scraped listing stores: source_platform, external_listing_id, external_url, scraped_at,
landlord_contact_email (if parseable).
Listings are tagged with a “Source” badge on the UI (e.g. “Via OnTheMove”) for transparency.
Scraping cadence: minimum every 24 hours. Removed external listings are flagged as ‘expired’.

9.2 Enquiry Routing for Scraped Listings
•
•
•

If landlord_contact_email is available: relay enquiry to that address using platform relay email.
If landlord_contact_email is not available: store enquiry in pending state. Notify internal team to
manually trace contact.
Platform clearly communicates to the tenant: “This listing is from an external source. We’ve
forwarded your enquiry and will update you.”

9.3 Compliance Considerations
•
•
•

All scraped listing enquiries must include opt-out / unsubscribe links in forwarded emails.
External landlords must be given the option to remove their listing from the platform in claim
emails.
Data from scraped listings must not be used for marketing without explicit consent.
